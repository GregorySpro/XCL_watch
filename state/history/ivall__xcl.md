# Historique : ivall/xcl

## État du projet

Après ce changement, le pipeline D3D12.X crée toujours correctement les SRV par défaut pour les tampons de profondeur multisamples et les ressources réservées sont correctement identifiées, tandis que les appels `Map` restent filtrés comme avant. Le fallback en mémoire du cache shader empêche les plantages liés à `CreateShaderCacheSession` et les tests unitaires passent (le test dédié au fallback réussit). Les blocages antérieurs (maillage, textures avancées, validation de couverture GPU) restent en place, et la prochaine étape probable (intégration du script d’exports PE dans la CI et prise en charge des gros blocs restants) n’est pas affectée par ce commit.

## Journal (du plus récent au plus ancien)

- **2026-11-24** `b7aa9f3` D3D12.X: fall back to an in-memory shader cache session (#1108)
  Le nouveau commit ajoute un fallback en mémoire pour les sessions de cache de shaders D3D12 lorsqu’une création via le runtime PC échoue. Cette implémentation s’insère dans la série de correctifs récents autour du fallback et du diagnostic (ex. flux de pipeline, signatures racine, allocation), en évitant les plantages immédiats des titres qui dépendaient du cache shader. Désormais les titres comme le build retail RAGE peuvent continuer à s’exécuter même si le runtime ne supporte pas `CreateShaderCacheSession`; le reste du pipeline reste inchangé et les limitations précédentes (maillage, textures avancées, validation GPU) subsistent.
- **2026-11-24** `c85ce8d` D3D12.X: a title's Map of a resource the PC cannot map does not reach the PC's Map
  Le commit corrige la fonction `res_map` afin que les appels `Map` d’un titre ne soient pas redirigés vers le `Map` du PC lorsqu’une ressource ne peut pas être mappée (heap DEFAULT, heap custom sans pages CPU, ou ressource réservée). Cette modification s’inscrit dans la série de correctifs récents sur la gestion des ressources D3D12.X, en particulier après les ajustements de création de vues et d’allocation. Désormais les titres utilisent directement l’adresse du titre pour ces ressources, évitant les erreurs 822/824 du debug layer, mais les ressources réellement mappables continuent d’utiliser le chemin PC.
- **2026-11-24** `fc0462b` D3D12.X: default SRVs of multisampled depth buffers are Texture2DMS views
  Le commit corrige la création de vues SRV par défaut pour les tampons de profondeur multisamples en les faisant apparaître comme Texture2DMS (ou Texture2DMSArray) au lieu de Texture2D/Texture2DArray. Cette modification s’inscrit dans la série de correctifs récents autour de la gestion des formats console et des clear values, en complétant le support des ressources depth déjà partiellement ajouté. Désormais les vues héritées respectent le nombre d’échantillons et la taille du tableau, ce qui rend les ressources depth multisamples valides pour les shaders. Le problème de vues incorrectes sur les buffers depth multisamples est résolu, mais les limitations majeures (maillage, textures avancées, couverture GPU Intel/NVIDIA) restent inchangées.
- **2026-11-24** `b9789a1` D3D12.X: CreatePlacedResource converts the clear value of a console format
  Le commit ajoute la conversion du clear value dans CreatePlacedResource lorsqu’on crée une ressource console, en appelant pc_clear avant les différents chemins d’allocation. Cette modification poursuit les correctifs récents autour de la gestion des formats et des clear values (similaire aux changements de CreateCommittedResource et CreatePlacedResourceX). Elle permet désormais de créer correctement des ressources depth + UAV en console format avec un clear value, évitant l’erreur E_INVALIDARG, mais les tests restent limités aux GPU AMD et aux scénarios de clear value explicite.
- **2026-11-24** `345661b` D3D12.X: depth+UAV buffers on the PC fallback paths start as depth writes
  Le nouveau commit introduit la fonction `pc_initial_state` qui ajuste l’état initial des ressources depth + UAV sur les chemins de repli PC, en remplaçant le bit `UNORDERED_ACCESS` par `DEPTH_WRITE` lorsque le tampon possède le flag `ALLOW_UNORDERED_ACCESS`. Cette modification s’insère dans la série de correctifs récents sur D3D12.X (alignement, flux de pipeline, limites de root signature) et résout le blocage où la création d’un tel tampon était refusée (E_INVALIDARG) ou rétrogradée en état `COMMON`. Désormais les textures depth + UAV peuvent être créées et placées correctement, même si les tests GPU restent limités aux cartes AMD récentes.
- **2026-11-24** `53657c6` D3D12.X: allocation info of several resources is padded to their alignment
  Le changement introduit une fonction `allocation_of` qui calcule correctement la taille totale d’un groupe de ressources en la ramenant à l’alignement le plus grand, conformément à la documentation Microsoft. Cela corrige le calcul erroné de `GetResourceAllocationInfo`/`GetResourceAllocationInfo1` où la somme était uniquement alignée per‑resource sans aligner le total. Le correctif s’inscrit dans la série de sécurisations du pipeline D3D12.X (vérifications d’overflow, limites de flux) et débloque désormais les scénarios où des ressources de tailles et alignements mixtes (ex. 64 KB, 4 MB, 64 KB) étaient sous‑allouées. Les fonctions de création de root signatures et les tests shaders restent inchangés, mais le calcul d’allocation est maintenant fiable.
- **2026-11-24** `f538b86` D3D12.X: a root signature with a huge constant count gets no layout
  Le commit ajoute des vérifications d’arithmétique sécurisée lors de la construction du layout d’une root signature D3D12.X, refusant les signatures dont le nombre de constantes dépasse 0x3FFF_FFFF ou dont la taille excède 4096 bytes. Cette modification poursuit la série de correctifs récents sur la robustesse du traitement des flux et des blobs, en éliminant les débordements qui provoquaient des panic en debug ou des allocations gigantesques en release. Désormais les titres qui demandent une root signature excessivement grande reçoivent simplement « no layout », évitant ainsi des plantages ou des échecs d’allocation. Les limites restent toutefois arbitraires (4096 bytes) et ne couvrent pas les cas où la console accepterait des tailles intermédiaires non documentées.
